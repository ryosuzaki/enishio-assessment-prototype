# Enishio Assessment Prototype

[![CI](https://github.com/ryosuzaki/enishio-assessment-prototype/actions/workflows/ci.yml/badge.svg)](https://github.com/ryosuzaki/enishio-assessment-prototype/actions/workflows/ci.yml)

## 1. 概要と位置づけ

生成AIが答えを出せる時代において、真に問われるのは静的な知識や成果物の出来ではない。**AIと協働しながら曖昧な要求を構造化し、出力を鵜呑みにせず検証・修正し、前提変化に適応して合意形成できるか（動的コンピテンシー4領域）**というプロセスそのものを、対話ログから証拠つきで抽出して評価・育成する。

本プロトタイプは、**「ビジネスの全体像（Viability）」**と**「コア技術の工学的実現可能性（Feasibility）」**を両立して実証する2層構造で構成されている。

1. **ビジネス全体像（Viability・モックUI）**: 企業のDX・人事責任者が何を見るのか（組織ダッシュボード）、受講者が日常的にどう成長するのか（受講者カルテ）、そして専門家のお手本や典型的な失敗行動を対比・復習できる事後講評基盤（行動比較ギャラリー）の利用サイクル全体を視覚化。
2. **中核評価エンジンの稼働（Feasibility）**: 1セッションが端から端まで通る縦切り（3ペイン動的対話・CFF・AutoSCORE 2段階採点・XAIレポート）を Next.js + PostgreSQL + LLM API で実装している。**検証の内訳は次のとおり。**(a) AutoSCORE の2段階（根拠抽出→バンド採点）は実APIキーで実行し、構造化出力が返ること・根拠要素が抽出されることを確認済み。(b) 画面遷移と分岐はE2E 11件で自動検証（**CIをAPIキー無しで回すためAPIルートはモックしており、ここでの検証範囲は画面の結線と分岐である**）。(c) 型検査・単体45件・本番ビルド・クライアントバンドルへの正答鍵非漏洩をCIで常時検査。

### ① 組織・受講管理ダッシュボード（Viability・モックUI）
* **対象**: 企業の技術部門長・エンジニアリングマネージャー（EM）、DX推進・人事育成担当者
* **提供価値**: 受講者個人の学習進捗と動的コンピテンシー（4領域）の成長推移を一元管理し、バイアス克服成果の実証と現場マネジメント（1on1・推奨課題）を支援
* **画面要素**:
  * **受講者一覧・スキル到達度カルテ（メイン）**: メンバー別の受講進捗、動的コンピテンシー4領域スコア（到達Band）、成長推移、詳細カルテへのドリルダウン導線
  * **バイアス克服・学習成果（Before / After）**: 初回演習 vs 直近演習における無検証承認率・過剰指摘率の改善推移（客観的な教育効果の実測）
  * **マネージャー向け育成アクション処方箋**: 未受講・停滞メンバーへのリマインド、弱点傾向に応じた推奨シナリオ配信、1on1指導ヒント
  * **部門別 運用・定着サマリー（サブ集計）**: 部署ごとの受講完了率、月間アクティブ率、平均演習セッション数（組織定着度の把握）
  * **受講履歴・学習時間データ出力（エクスポート）**: 厚生労働省の人材開発支援助成金（リスキリング支援コース・10〜12時間要件）申請や社内報告用の受講ログCSV出力

### ② 受講者マイページ・スキルカルテ（Viability・モックUI）
* **対象**: 受講者（ソフトウェアエンジニア）本人
* **提供価値**: 1回15〜30分の実務演習を通じて、AI協働プロセス（検証アプローチ・思考の癖・好手）を客観的エビデンスに基づき自己省察し、現場の実務（要件定義・設計・レビュー・AI協働）ですぐに使える判断軸と成長を実感する
* **画面要素**:
  * **動的コンピテンシー4領域・12サブ観点レーダー＆詳細ブレークダウン**: 4大領域（評価的判断力・高次認知・対話共創・適応力）および各3つのサブ観点（構造的欠陥特定、正常箇所の弁別、トレードオフ統合、前提変化への適応等）の到達度と発話ログエビデンス
  * **協働アプローチ特性プロファイル（適正依存バランス）**: リスク防御力（CSR）と協働活用効率（CAR）のバランスから、個人の検証スタイルの強みと更なる成長の着眼点を提示
  * **演習ハイライト・好手（Good Moves）ログ**: AI同僚の反論を論理的に覆した発話や、前提変化に即応した設計判断など、優れた検証行動のエビデンス抽出
  * **実務転移チェックリスト（Takeaways）**: 演習から得られた「明日からの実務（要件定義・設計・レビュー・AI協働）で意識すべき自分専用の確認観点」
  * **セッション履歴と成長推移**: 過去の演習セッションにおける到達度推移と手戻り削減傾向

### ③ シナリオ分析＆エキスパート事後講評（Viability・モックUI ＆ 事後デブリーフィング）
* **対象**: 受講者（演習後の復習・腹落ち）、EM・テックリード、人事育成責任者
* **提供価値**: 受講者の心理的安全性を第一に設計。個人名・生ログ・評価的ラベリング（「典型的な失敗」「若手の罠」等）を完全排除し、客観的な行動テレメトリに基づき「AIの欺瞞トリック」「上位者の複数攻略ルート」「動的コンピテンシー別の客観的行動と自身の伸び代」を突合できる事後講評（Debriefing）を提供。
* **画面要素（3層構造）**:
  * **Layer 01: 課題トラップ構造の解剖（AIのミスリードと認知バイアス）**:
    * AIが仕掛けた欺瞞のメカニズム（テストケースの密かな削除、流暢な解説による隠蔽など）の解剖
    * 人間が陥りやすい心理的脆弱性（緑のチェックマークへの確証バイアス、権威性バイアスなど）と受講者全体の遭遇率（例: 67%）を提示
  * **Layer 02: 上位者の攻略ルート分岐図（価値中立な戦略比較）**:
    * 正解を1つに絞らず、上位者（Level 4〜5）が採用した複数の有効なアプローチを比較
    * ルートA: テスト駆動アプローチ（異常系テストを自作・実行させてバグを炙り出す / 採用率 52%）
    * ルートB: 仕様整合アプローチ（Slack経緯や外部規約の矛盾を突く / 採用率 31%）
    * ルートC: 差分・アーキテクチャ精読アプローチ（SPOFや障害シナリオを突く / 採用率 17%）
  * **Layer 03: 動的コンピテンシー別・上位者メタ行動と自己ハイライト**:
    * 思考の当て推量（脳内モノローグ）を排し、観測された客観的テレメトリ（プロンプト・テスト実行・差分確認）から抽出した上位者のメタ行動を提示
    * Enishioの動的コンピテンシー4領域（評価的判断力、高次認知・動的思考、対話的共創力、メタ認知・適応力）別に上位者実施率（例: 92%）と全体平均（例: 26%）を対比
    * 受講者本人のセッション結果を自動突合（✅ 達成済 / ⭕️ 部分的 / 💡 伸び代）し、次回への具体的なアクション指針・問いかけ例を提示
  * **インタラクティブ機能**: 課題の切り替え（FinTech/EC/社内AI）、達成状況フィルター（伸び代のみ/達成済のみ）、演習セッションへの再挑戦CTA

### ④ 動的実務演習セッション（Feasibility・実稼働経路）
* **対象**: 受講演習の実行、技術的実現可能性の検証
* **セッションの動作フロー**:

```
[STEP 1: 共通アンカー出題] ─→ [STEP 2: 実務課題対話] ─→ [STEP 3: CFF事前判定] ─→ [STEP 4: AutoSCORE採点] ─→ [STEP 5: XAIレポート]
```

| ステップ | 名称 | 概要・受講者の体験 |
| :--- | :--- | :--- |
| **STEP 1** | **共通アンカー出題** | 共通アンカー項目へ回答。採点機の厳格度ドリフトを検知する固定基準点として無得点で客観記録（LLM採点を通さず循環遮断・初回必須＋以降7回に1回運用）。形式は状況変化に対する判断更新を問う**疑似対話形式（SCT型・4段構成）**で、段階1=採用可否／段階2=懸念領域（提示順をサーバでシャッフルし記録）／段階3=前提変化への判断更新（-2..+2）／段階3'=新情報を含まない反論への再回答。 |
| **STEP 2** | **実務課題対話（3ペイン環境）** | 要件仕様・コード・AIチャットを統合した環境でAI同僚と協働。進行役（メディエーター）が状況に応じて深掘りを介入。 |
| **STEP 3** | **CFF（認知強制機能）** | AI採点開示前に、受講者自身が成果物を［承認］または［差し戻し］判定。進行役が対話から整理した論点要約を確認して確定。 |
| **STEP 4** | **AutoSCORE（2段階自動採点）** | 対話ログから検証行動を抽出（第1段階）し、その根拠のみをもとにルーブリック採点（第2段階）。確信度不足時は人間の確認待ち（pending_human）で保留。 |
| **STEP 5** | **XAIレポート** | 採点根拠となった発言のハイライト、形成的フィードバック、受講者の事前判定との対照結果を表示。 |

> 💡 **全ステップの行動ログ（テレメトリ）は、バックエンドのPostgreSQLデータベース（14テーブル）へリアルタイムに本番スキーマで記録されます。**
> 
> ※ `OPENAI_API_KEY` が無い場合は実務課題対話〜採点（STEP 2〜4）は動作しません（代わりのローカル判定は置いていません）。なお、①組織ダッシュボード、②受講者カルテ、③エキスパート事後講評、およびアンカー出題・ログ基盤はAPIキー不要で即座に閲覧・体験可能です。

#### 主要画面スクリーンショット

* **3ペイン動的演習環境**:
  * **第1ペイン（左）**: 「業務要件・制約条件」と「社内Slack協議ログ（開発の経緯）」のサブタブ切り替え。
  * **第2ペイン（中央）**: 「実装コード」と「ユニットテストコード (*.test.ts)」のサブタブ切り替え（正常系のみ通過するハッピーパストラップを同梱）。受講者がAI同僚を説得した場合は修正コードが即座に再生成・自動反映。
  * **第3ペイン（右）**: 意図確認CFF、AI同僚チャット（トレードオフ自説弁護）、進行役によるソクラテス型深掘り、コード差分確認、AutoSCORE評価実行ボタンを統合。

## 3. 設計上の判断

| 判断 | 理由 |
| :--- | :--- |
| **ログスキーマだけは本番仕様で作る** | UIは捨ててよいがログ定義は捨ててはならない。後から足したフィールドは過去セッション分を永久に失う。ここを本番仕様にしておけば実装がそのまま上に乗る |
| **抽出と採点を2つのエージェントに分ける** | 採点器に生ログを渡すと「何を根拠に何点にしたか」が事後に分離できない。抽出結果のみを採点入力にすることで、根拠と得点の対応がログ上で追跡可能になる |
| **`temperature: 0` に依存しない** | 現行モデルで当該パラメータは利用できない。出力形式は Structured Outputs の型拘束で確保し、`scorer_model_version`（モデルID＋抽出版＋採点版の複合文字列）の全評点記録により追跡可能性を担保する |
| **採点軸を1本に絞る** | 複数軸を同時採点すると項目間の局所依存が生じ、実効項目数が落ちる。縦切りでは軸を1本に固定する |
| **採点できないときは採点しない** | APIキーが無い・構造化出力が得られない場合に、キーワード一致等のローカル判定で代替しない。代替すると (a) 単語の出現を検証行動として測ってしまい、(b) LLMが走っていないのに `rater_type = "llm"` のログが残って `scorer_model_version` による追跡可能性が崩れる。**採点しないほうが正確である** |
| **確信度が低い判定は確定させない** | 採点器が自己申告した確信度が 0.70 を下回る判定は `rater_type = "pending_human"` ・`rating_category = null` として記録する。推定器が迷った事実を潰さずに残す |
| **単一スタックで通す** | Python 側の処理（IRT較正等）は本縦切りのスコープ外。短期間で端から端まで通すことを優先した |
| **アンカーをLLM採点器に通さない** | アンカーの評点まで同じLLM採点器が出すと、採点器のばらつきや厳格度ドリフトを検出する基準点がその採点器自身になり循環する。固定点は採点器の外側に置かなければ基準点として機能しない。そのため無得点で記録し、客観判定をとる |
| **アンカーを疑似対話形式（SCT型）にする** | 静的な選択式では選択肢が答えを含むため「言われずに気づく」という測定対象そのものが消え、対話側とは別の構成概念を測ってしまう。段階1〜3' の4段構成へ置き換え、固定選択のまま（＝決定論的採点とLLM非依存を保つ）判断の更新を追えるようにした。段階3は正答鍵ではなく専門家パネルの応答分布で採点する。バンクの本格構築（20項目・パネル分布の実データ化）とチート耐性の定量実測は本格開発フェーズに行う |
| **成果物の全量保存による比較判断（CJ）経路の確保** | 相対尺度として後続フェーズにLLMペア比較判定（Bradley-Terry）を適用できるよう、最終成果物をセッション終了・採点時に `artifact_edit_distance_series` へ全量永続化する |
| **対話側に測定モデルを置かない** | 動的に生成される一回性の課題には項目パラメータの同定可能性が無い。対話側は中間表現に基づくルーブリック基準参照評価（0〜5バンド）に留め、アンカー側の尺度と同一尺度化しない |
| **CFFにおける対話内ミラーリングとPRレビュー形式の統合** | 受講者の認知負荷を抑えつつ、評価レポート閲覧前の最終判断と根拠を確実にコミットさせるため、進行役が対話ログから整理した論点要約を提示し、実務になじむGitHub PRレビュー形式で［承認］［差し戻し］をワンクリック確定する設計とした |

## 5. データモデル

`prisma/schema.prisma` に14テーブル。評点の正本は `Rating`。

| テーブル | 役割 |
| :--- | :--- |
| `Learner` / `Session` | `session_seq` を明示的に持つ（中断・再開・削除が混じるため日時から復元できない）。`Session` は `window_blur_duration_sec`（画面外滞在時間・記録専用で判定には使わない）も持つ |
| `Rating` | 評点の正本。`scorer_model_version` / `stimulus_type` / `anchor_status` / `stimulus_features`(JSONB) / `probe_consistency_score`。`rating_category` は nullable で、null は「未採点」（人間の確認待ち）を表す |
| `AnchorItem` / `AnchorResponse` | 較正用アンカー項目とその応答。`pretest` / `operational` の2状態。**アンカーは無得点なので `Rating` に行を作らない**——0点を入れるとルーブリック上の「Level 0」と区別できなくなり、将来の較正を汚す。応答時点の `anchor_status` は `AnchorResponse` 側に凍結して持つ |
| `PromptTurn` | 対話の全ターン全文。`role` は `user` / `assistant` / `mediator` を区別する |
| `ArtifactEditDistanceSeries` | 成果物の編集距離の時系列および最終成果物の全量保存（Bradley-Terry比較判断経路） |
| `InjectedFlawMap` | 仕込んだ誤りの位置と類型、**および正常箇所のラベル**（これがないと過剰指摘を判定できない） |
| `LearnerPreliminaryJudgement` | CFF（Force Decision First / Mandatory Justification）による事前暫定判断。進行役による対話内論点ミラーリング要約に対するコミットメント（承認/差し戻し、および確認理由記述）を記録 |
| `VerificationFocusSequence` | 3ペイン検証パネルで受講者が選択したコードスパンと明示順序（`focus_seq`） |
| `ScoreFeedback` | 異議申立。自由記述の理由を必須にしている |
| `EvidenceComponent` | 採点エンジン第1エージェントが抽出した根拠要素。評点だけでなく根拠そのものを永続化し、XAIレポートのハイライトの原材料にもなる |
| `RelianceMetrics` | 適正依存の3指標（リスク防御力 CSR / 協働活用効率 CAR / 自動化バイアス ABI）。過剰指摘トラップ（正常箇所）と仕込み不備の両方に対する判断から算出 |
| `MediationProbe` | ソクラテス型深掘り・What-if注入の1手ごとの状態推定・選んだ手・選定理由。**正答鍵は含まない**（誘出であって誘導ではないため） |

## 6. 動かす

このリポジトリを clone しただけの状態から、5コマンドで通る。

```bash
npm install
cp .env.example .env      # DATABASE_URL はそのままで docker-compose の設定と一致する
docker compose up -d      # ローカル PostgreSQL（別途用意した DB を使うなら不要）
npm run prisma:generate && npm run prisma:push
npm run seed:anchors      # アンカー項目を anchor_items へ投入（これが無いと出題が落ちる）
npm run dev
```

`OPENAI_API_KEY` を `.env` へ設定すると ②〜⑤（AI同僚との対話・AutoSCORE採点・XAIレポート）まで通る。未設定でも ① アンカー出題と ⓪ ログ基盤は動く。

詳細なステップ・バイ・ステップの画面操作手順、テレメトリ確認項目、トラブルシューティングについては、[プロトタイプ動作確認手順書](docs/プロトタイプ動作確認手順書.md) を参照。

### アンカー項目バンクの2つの供給源

探索順は次のとおり。**サンプルを運用バンクに見せない。退役形式を現行形式に見せない。**どれを読んだかは `source` として返し、画面にも明示する。

| 順 | 供給源 | 中身 |
| :--- | :--- | :--- |
| 1 | `src/data/anchors.v2.json` | 運用バンク（現行形式 v2-sct）。`.gitignore` 済み |
| 2 | `src/data/anchors.v2.sample.json` | **公開デモ用サンプル3項目**（現行形式・リポジトリ同梱） |
| 3 | `src/data/anchors.json` | 運用バンク（**v1・退役**） |
| 4 | `src/data/anchors.sample.json` | 公開デモ用サンプル（**v1・退役**） |

**clone しただけの状態では 2 が読まれる。**現行形式の全4段（類型Cの分岐を含む）がそのまま動く。

v1 を退役させた理由は README §4 の設計判断表を参照。**較正・等化に用いてはならない。**

**運用バンクはこのリポジトリに含まれていない。**項目そのものを公開すると受検者が事前に読めてしまうためである（項目露出。MVP 2.6.2 の監視指標）。v1 素材の生成には隣の `enishio-education` リポジトリのチェックアウトが要る:

```bash
git -C ../.. submodule update --init products/enishio-education
npm run parse:anchors     # Markdown → src/data/anchors.json
npm run seed:anchors
```

同梱サンプルで動かしている間は、**出題画面に「公開デモ用サンプル」と明示される。**
項目の中身は運用バンクと異なるが、出題から `anchor_responses` への無得点記録までの経路は同一である。

ログ基盤だけを単体で確かめる場合は `npm run seed`（DBへ書き込む検証スクリプト）。

### テスト・検証スクリプト

```bash
npm run test                  # 単体テスト（Vitest 45件）
npm run test:e2e              # E2Eテスト（Playwright 11シナリオ）
npm run capture:screenshots   # UIスクリーンショット取得（docs/screenshots/ へ高解像度出力）
```

生成に `DATABASE_URL` の存在自体は要るため、DB を立てずに走らせる場合はダミーを渡す。

```bash
DATABASE_URL="postgresql://dummy:dummy@127.0.0.1:5432/dummy" npm run test:e2e
```

## 7. 公開デプロイ手順

Vercel + サーバーレス PostgreSQL（Supabase / Neon）への公開デプロイ手順です。

### 1. サーバーレス PostgreSQL の準備
1. [Supabase](https://supabase.com) または [Neon](https://neon.tech) で新規プロジェクトを作成します。
2. 接続文字列（Connection String）を取得します。
   - **Prisma 接続プーリングの注意点**: Vercel 等のサーバーレス環境では接続過多（Connection Exhaustion）を防ぐため、**プーリング接続文字列（Transaction pooler / ポート 6543 / `?pgbouncer=true`）** を使用してください。
   - 例: `postgresql://postgres:[PASSWORD]@[HOST]:6543/postgres?pgbouncer=true&connection_limit=1`

### 2. スキーマ適用とアンカーデータの初期シード
デプロイ前に、手元の環境から対象データベースに対してスキーマとアンカー項目を投入します。
```bash
# 接続先を対象のデータベースURLに設定して実行
export DATABASE_URL="postgresql://postgres:[PASSWORD]@[HOST]:6543/postgres?pgbouncer=true"

# スキーマの反映（14テーブル作成）
npx prisma db push

# アンカー項目のパースとDB初期シード
npm run parse:anchors
npm run seed:anchors
```

### 3. Vercel へのインポートと環境変数設定
1. [Vercel](https://vercel.com) でリポジトリをインポートします。
   - **Framework Preset**: `Next.js`
   - **Build Command**: `next build`（デフォルトのままで可）
2. **Environment Variables** に以下を設定します:
   - `DATABASE_URL`: 手順1で取得したプーリング接続文字列
   - `OPENAI_API_KEY`: LLM API キー
   - `GEMINI_API_KEY`: （任意）Google Gemini API キー

### 4. デプロイと動作検証
1. **Deploy** を実行します。
2. デプロイ完了後、発行された URL にアクセスし、以下を確認します:
   - トップページでアンカーがロードされること
   - 「セッションを開始する」でアンカー出題へ進めること
   - 動的課題の対話および AutoSCORE 2段階採点が正常に動作し、XAIレポートが表示されること

## 8. 意図的に作っていないもの（今後の開発スコープ）

本プロトタイプは「全体像（Viability）」と「コア評価技術の稼働（Feasibility）」の証明に集中しており、以下の要素は今後の本格開発・社会実装スコープとして意図的に切り離している：

* **疑似対話形式（SCT型）アンカーバンクの本格構築とチート耐性実測**: 形式（段階1〜3' の4段構成）と出題〜無得点記録パイプラインは実装済みだが、同梱しているのはサンプル3項目であり、段階3の専門家パネル分布はモック値である。20項目規模のバンク作成、パネル分布の実データ化、およびマルチLLMによるチート耐性の定量実測は後続フェーズに実施する。
* **管理画面・カルテ・行動比較ギャラリーの本番バックエンド**: 組織ダッシュボード、受講者カルテ、およびシナリオ別行動比較ギャラリーはモックUI（Prismaスキーマ準拠の静的データ）として全体像を提示している。実運用ではDBに蓄積された受講者の実ログから各バンドの代表的セッションを自動集約・抽出する。マルチテナントDB、ロール別権限・認証・SSO、本番リアルタイム集計パイプライン、課金管理は商用化に向けて開発する。
* **実務題材・誤り注入パイプラインの自動生成**: 現状は人手作成3シナリオから選択。要件定義〜設計工程の実務題材を体系的かつ動的に生成・誤り注入するパイプラインを構築する。
* **比較判断（Bradley-Terry）判定器・セマンティックDiff**: 現行の絶対採点方式から、課題横断での人間専門家一致（QWK $\ge 0.70$）を担保する判定パイプラインを実装する。
* **評価者HITL画面 / IRT較正・等化パイプライン**: 提携企業でのPoCおよびSMEパネルを通じた実データ収集を経て構築・較正する。
