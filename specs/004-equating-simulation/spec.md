# Feature Specification: 共通尺度化エンジンの合成データ検証 (004-equating-simulation)

> **ステータス**: Approved / Implemented
> **対象レイヤー**: 検証用シミュレーション（本番の採点経路には接続しない）
> **全体アーキテクチャ**: [specs/README.md](../README.md)

---

## 1. 概要とユーザー価値 (What & Why)

### 1.1 解決する課題
提案の中核である共通尺度化エンジン（第1層：証拠の一対比較＋Bradley-Terry、第2層：固定設問と凍結ペア判定による定点較正）は、事業期間中に実データで実装・検証する。
しかし実装前の段階でも、**統計的な仕組みとして筋が通っているか**は合成データで確かめられる。確かめないまま実装に入ると、「どの条件なら成り立ち、どの条件なら崩れるか」が分からず、PoC で何を測ればよいかも決まらない。

### 1.2 提供価値・ゴール
1. 受講者ごとに課題の難易度が違うとき、絶対採点と一対比較＋Bradley-Terry のどちらが真の実力を回復できるかを、条件を変えて比べられる。
2. 判定器のズレと受講者の実力変化が同時に起きうるとき、第2層の2本の外部基準（固定設問・凍結ペア判定）で両者を切り分けられるかを確かめられる。
3. 結果が乱数種で再現でき、仮定したパラメータが結果と一緒に出力される。

### 1.3 この検証が示さないこと（境界）
* **LLM 判定器が実際にこのモデルの仮定を満たすかは示さない。**特に「一対比較の判定器は課題難易度の影響をどこまで取り除けるか」（本文の λ）は、事業期間中に人間専門家の判定との一致率（到達目標4）で実測する対象である。
* 合成データの数値を、提案書の到達目標の達成見込みとして引用しない。

## 2. ユーザーストーリーと受入基準 (Acceptance Criteria)

### [US1] Bradley-Terry 推定器
* **Given**: 受講者の勝敗記録（誰が誰に勝ったか）がある。
* **When**: `fitBradleyTerry` を実行する。
* **Then**:
  * 各受講者の能力値（対数強度）が、平均0に中心化されて返る。
  * 全勝・全敗の受講者がいても発散しない（仮想対戦による弱い事前分布で正則化する）。
  * 既知の強度から生成した十分な対戦データに対し、推定値と真値の順位相関が 0.9 を超える。

### [US2] 実験1：課題難易度の交絡
* **Given**: 受講者ごとに固有の課題難易度 b を持つ合成集団（課題の共有なし）。
* **When**: 同じ受講者を (a) 自分の課題での絶対採点（0〜5バンド）と、(b) 他の受講者との一対比較＋Bradley-Terry で並べる。
* **Then**: 判定器に残る難易度の影響 λ（0＝完全に取り除ける、1＝絶対採点と同じだけ残る）と、1人あたりの比較回数 k を変えたときの、真の実力との順位相関が出力される。

### [US3] 実験2：実力変化と判定器のズレの切り分け
* **Given**: 基準期のコホートAと次期のコホートB。次の3シナリオを置く。
  * (a) Bの実力が上がり、判定器は変わらない。
  * (b) Bの実力は同じだが、判定器の版が変わり、実力と無関係な表層特徴（文章量など）を評価し始める。Bはその特徴が強い。
  * (c) (a) と (b) が同時に起きる。
* **When**: 第1層（A・Bを結合した Bradley-Terry）、第2層(1)（固定設問の得点、LLMを通さない）、第2層(2)（凍結ペアでの新旧判定器と人間判定の一致率）を計算する。
* **Then**: 各シナリオで、第1層が示す「伸び」、固定設問が示す「伸び」、凍結ペア一致率の変化が出力され、2つの外部基準の組み合わせでシナリオを判別できるかが分かる。

### [US4] 再現性と出力
* `npm run sim:equating` で実行でき、LLM API・DB を使わない。
* 同じ乱数種なら同じ結果を返す。
* `docs/equating-simulation/` に結果の Markdown と図（SVG）を書き出し、仮定したパラメータを併記する。
