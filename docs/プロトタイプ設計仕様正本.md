## 1. 概要と位置づけ

生成AIが答えを出せる時代において、真に問われるのは静的な知識や成果物の出来ではない。**AIと協働しながら曖昧な要求を構造化し、出力を鵜呑みにせず検証・修正し、前提変化に適応して合意形成できるか（動的コンピテンシー4領域）**というプロセスそのものを、対話ログから証拠つきで抽出して評価・育成する。

本プロトタイプは、**「ビジネスの全体像（Viability）」**と**「コア技術の工学的実現可能性（Feasibility）」**を両立して実証する2層構造で構成されている（`[D-79]`）。

1. **ビジネス全体像（Viability・モックUI）**: 企業のDX・人事責任者が何を見るのか（組織ダッシュボード）、受講者が日常的にどう成長するのか（受講者カルテ）の利用サイクル全体を視覚化。
2. **中核評価エンジンの稼働（Feasibility）**: 1セッションが端から端まで通る縦切り（3ペイン動的対話・CFF・AutoSCORE 2段階採点・XAIレポート）を Next.js + PostgreSQL + LLM API で実装している。**検証の内訳は次のとおり。**(a) AutoSCORE の2段階（根拠抽出→バンド採点）は実APIキーで実行し、構造化出力が返ること・根拠要素が抽出されることを確認済み。(b) 画面遷移と分岐はE2E 10件で自動検証（**CIをAPIキー無しで回すためAPIルートはモックしており、ここでの検証範囲は画面の結線と分岐である**）。(c) 型検査・単体45件・本番ビルド・クライアントバンドルへの正答鍵非漏洩をCIで常時検査。

## 2. 画面構成と利用サイクル

画面上部のタブナビゲーションにより、以下の3つの画面を切り替えて体験できる。

```
┌────────────────────────────────────────────────────────────────────────┐
│  [Enishio Platform]   ① 組織ダッシュボード  |  ② 受講者カルテ  |  ③ 演習セッション │
└────────────────────────────────────────────────────────────────────────┘
```

### ① 組織・受講管理ダッシュボード（Viability・モックUI）
* **対象**: 企業の技術部門長・エンジニアリングマネージャー（EM）、DX推進・人事育成担当者
* **提供価値**: 受講者個人の学習進捗と動的コンピテンシー（4領域）の成長推移を一元管理し、バイアス克服成果の実証と現場マネジメント（1on1・推奨課題）を支援
* **画面要素**:
  * **受講者一覧・スキル到達度カルテ（メイン）**: メンバー別の受講進捗、動的コンピテンシー4領域スコア（到達Band）、成長推移、詳細カルテへのドリルダウン導線
  * **バイアス克服・学習成果（Before / After）**: 初回演習 vs 直近演習における無検証承認率・過剰指摘率の改善推移（客観的な教育効果の実測）
  * **マネージャー向け育成アクション処方箋**: 未受講・停滞メンバーへのリマインド、弱点傾向に応じた推奨シナリオ配信、1on1指導ヒント
  * **部門別 運用・定着サマリー（サブ集計）**: 部署ごとの受講完了率、月間アクティブ率、平均演習セッション数（組織定着度の把握）
  * **受講履歴・学習時間データ出力（エクスポート）**: 厚生労働省の人材開発支援助成金（リスキリング支援コース・10〜12時間要件）申請や社内報告用の受講ログCSV出力

### ② 受講者マイページ・スキルカルテ（Viability・モックUI）
* **対象**: 受講者（ソフトウェアエンジニア）本人
* **提供価値**: 1回15〜30分の実務演習を通じて、AI協働プロセス（検証アプローチ・思考の癖・好手）を客観的エビデンスに基づき自己省察し、現場の実務（要件定義・設計・レビュー・AI協働）ですぐに使える判断軸と成長を実感する
* **画面要素**:
  * **動的コンピテンシー4領域・12サブ観点レーダー＆詳細ブレークダウン**: 4大領域（評価的判断力・高次認知・対話共創・適応力）および各3つのサブ観点（構造的欠陥特定、正常箇所の弁別、トレードオフ統合、前提変化への適応等）の到達度と発話ログエビデンス
  * **協働アプローチ特性プロファイル（適正依存バランス）**: リスク防御力（CSR）と協働活用効率（CAR）のバランスから、個人の検証スタイルの強みと更なる成長の着眼点を提示
  * **演習ハイライト・好手（Good Moves）ログ**: AI同僚の反論を論理的に覆した発話や、前提変化に即応した設計判断など、優れた検証行動のエビデンス抽出
  * **実務転移チェックリスト（Takeaways）**: 演習から得られた「明日からの実務（要件定義・設計・レビュー・AI協働）で意識すべき自分専用の確認観点」
  * **セッション履歴と成長推移**: 過去の演習セッションにおける到達度推移と手戻り削減傾向

### ③ 動的実務演習セッション（Feasibility・実稼働経路）
* **対象**: 受講演習の実行、技術的実現可能性の検証
* **セッションの動作フロー**:

```
[STEP 1: 共通アンカー出題] ─→ [STEP 2: 実務課題対話] ─→ [STEP 3: CFF事前判定] ─→ [STEP 4: AutoSCORE採点] ─→ [STEP 5: XAIレポート]
```

| ステップ | 名称 | 概要・受講者の体験 |
| :--- | :--- | :--- |
| **STEP 1** | **共通アンカー出題** | 共通アンカー項目へ回答。採点機の厳格度ドリフトを検知する固定基準点として無得点で客観記録（LLM採点を通さず循環遮断・初回必須＋以降7回に1回運用）。形式は**疑似対話形式（SCT型・4段構成 v2-sct）**で、段階1=採用可否／段階2=懸念領域（提示順をサーバでシャッフルし記録）／段階3=前提変化への判断更新（-2..+2）／段階3'=新情報を含まない反論への再回答（§3 の設計判断表を参照）。 |
| **STEP 2** | **実務課題対話（3ペイン環境）** | 要件仕様・コード・AIチャットを統合した環境でAI同僚と協働。進行役（メディエーター）が状況に応じて深掘りを介入。 |
| **STEP 3** | **CFF（認知強制機能）** | AI採点開示前に、受講者自身が成果物を［承認］または［差し戻し］判定。進行役が対話から整理した論点要約を確認して確定。 |
| **STEP 4** | **AutoSCORE（2段階自動採点）** | 対話ログから検証行動を抽出（第1段階）し、その根拠のみをもとにルーブリック採点（第2段階）。確信度不足時は人間の確認待ち（pending_human）で保留。 |
| **STEP 5** | **XAIレポート** | 採点根拠となった発言のハイライト、形成的フィードバック、受講者の事前判定との対照結果を表示。 |

> 💡 **全ステップの行動ログ（テレメトリ）は、バックエンドのPostgreSQLデータベース（14テーブル）へリアルタイムに本番スキーマで記録されます。**
> 
> ※ `OPENAI_API_KEY` が無い場合は実務課題対話〜採点（STEP 2〜4）は動作しません（代わりのローカル判定は置いていません）。なお、①組織ダッシュボード、②受講者カルテ、およびアンカー出題・ログ基盤はAPIキー不要で即座に閲覧・体験可能です。

## 3. 設計上の判断と根拠

| 判断 | 理由 |
| :--- | :--- |
| **ログスキーマだけは本番仕様で作る** | UIは捨ててよいがログ定義は捨ててはならない。後から足したフィールドは過去セッション分を永久に失う。ここを本番仕様にしておけば実装がそのまま上に乗る |
| **抽出と採点を2つのエージェントに分ける** | 採点器に生ログを渡すと「何を根拠に何点にしたか」が事後に分離できない。抽出結果のみを採点入力にすることで、根拠と得点の対応がログ上で追跡可能になる |
| **`temperature: 0` に依存しない** | 現行モデルで当該パラメータは利用できない。出力形式は Structured Outputs の型拘束で確保し、`scorer_model_version`（モデルID＋抽出版＋採点版の複合文字列）の全評点記録により追跡可能性を担保する |
| **縦切りでは採点軸を1本に絞る** | 端から端まで通すことを優先したスコープ限定であり、**多軸採点を否定するものではない**。本番SaaSでは軸別バンドを提示する（`[P-16]`）。局所依存（LID）・実効項目数の議論が効くのは尺度を構成するアンカー層であり、測定モデルを置かない対話側の基準参照バンドには適用されない |
| **採点できないときは採点しない** | APIキーが無い・構造化出力が得られない場合に、キーワード一致等のローカル判定で代替しない。代替すると (a) 単語の出現を検証行動として測ってしまい、(b) LLMが走っていないのに `rater_type = "llm"` のログが残って `scorer_model_version` による追跡可能性が崩れる。**採点しないほうが正確である** |
| **確信度が低い判定は確定させない** | 採点器が自己申告した確信度が 0.70 を下回る判定は `rater_type = "pending_human"` ・`rating_category = null` として記録する。推定器が迷った事実を潰さずに残す |
| **単一スタックで通す** | Python 側の処理（IRT較正等）は本縦切りのスコープ外。短期間で端から端まで通すことを優先した |
| **アンカーをLLM採点器に通さない** | アンカーの評点まで同じLLM採点器が出すと、採点器のばらつきや厳格度ドリフトを検出する基準点がその採点器自身になり循環する。固定点は採点器の外側に置かなければ基準点として機能しない（`[D-73]`）。そのため無得点で記録し、客観判定をとる |
| **アンカーを4段構成の疑似対話形式（v2-sct）で実装する** | 静的選択式（v1）は**選択肢が答えを含むため「言われずに気づく」という測定対象を消していた**——対話演習とは別の構成概念を測る形式であり、等化のアンカーとして成立しない（`[D-83]`）。回復手段は3つで、いずれも固定選択のまま＝決定論的採点とLLM非依存を保てる。**①段階的開示**（段階1で「採用可否」だけを確定・ロックしてから細部へ降りる）**②前提変化の注入**（段階3で新情報を出し、判断の移動をリッカートで取る＝SCT型）**③類型Cの混在**（不備の無い項目を混ぜ、「とりあえず条件付きを選ぶ」戦略を潰す）。回復しないのは「反論への応答（押し返す）」で、これは対話側に残る |
| **段階3を正答鍵ではなく専門家パネルの応答分布で採点する** | 単一の正答を置くと、消去法と外部LLMへの代行がそのまま効く。SCT の aggregate scoring に倣い、専門家パネル（技術判断の専門家10〜15名・`[D-82]` 決定3）の分布との一致で採点する。**パネル未組成の間は `panel.status = "mock"` とし、採点値を算出しない**——実在しない基準を実在するように見せないため |
| **一部の項目に段階3'（新情報を含まない反論）を置く** | 「押し返す」は (4a) 迎合しない と (4b) 説得する に分かれ、**前者は選択式で測れる**（`[D-83]`）。自信の表明・一般論への訴え・同調圧力だけを提示して同じ設問を再提示し、**段階3との差分**（`stage3b - stage3`）で採点する。0 なら保持、提案側へ動けば迎合（過剰依存 $P(R_{accept} \mid A_i)$）。**差分採点なので専門家パネルを要さず、段階3の鍵が mock の間も実データが出る唯一の軸である。**⚠️ 露出で劣化するため全項目には付けない。**画面に総段数を出さない**——「段階 1 / 5」と出せば、その項目に反論があることが最初から読める |
| **正誤もパネル分布も受検者へ返さない** | アンカーは採点器のドリフトを検出する固定基準点である。受検者へ結果を返せば、それ自体が学習材料になり**基準点のほうが回を追うごとに動く**（`[D-83]`）。完了画面の設計注記は「開発者向け」と明示して囲う |
| **選択肢をサーバでシャッフルし、提示順を記録する** | v1 運用バンク20項目は**両設問とも正答がキー A に固定**で、シャッフルも無く「A, A」で満点が取れた（`[D-83]`）。段階2はシャッフルし、`stage2_order` として応答と一緒に保存する——記録しなければ後から応答を解釈できない。段階1（採用可否）と段階3（リッカート）は順序に意味があるためシャッフルしない |
| **v1 バンクを退役させ、素材だけ再利用する** | 較正・等化に用いてはならない（`[D-83]`）。再利用してよいのは `intro` / `proposal` / `hidden_premise` のテキストのみで、これらは形式に依存しない素材であり、v2 の段階3（新情報）を書く材料にもなる。読み込み時の供給源は画面と seed スクリプトの双方で明示し、**退役形式を現行形式に見せない** |
| **アンカー出題は動的課題の縮図ではなく「一場面（マイクロシチュエーション）」を切り取る** | 目標・受入基準・スコープ外といったプロジェクト仕様書を1問に詰め込むとスコープが広すぎて非現実的になり、1問あたりの所要時間・認知負荷も肥大化して等化に必要な15〜20項目（`[D-82]`）を満たせなくなる。アンカーは実務のコードレビューや設計判断の決定的瞬間（2〜3文のヴィネット）をシャープに切り取って出題する（`[D-86]`） |
| **成果物の全量保存による比較判断（CJ）経路の確保** | 相対尺度として後続フェーズにLLMペア比較判定（Bradley-Terry）を適用できるよう、最終成果物をセッション終了・採点時に `artifact_edit_distance_series` へ全量永続化する（`[D-74]`） |
| **対話側に測定モデルを置かない** | 動的に生成される一回性の課題には項目パラメータの同定可能性が無い。対話側は中間表現に基づくルーブリック基準参照評価（0〜5バンド）に留め、アンカー側の尺度と同一尺度化しない |
| **CFFにおける白紙再作文の恒久禁止と対話内ミラーリング統合** | 15分間の対話を終えた受講者に別画面で白紙から理由を再作文させることは認知負荷の二重請求であり参加コストを暴騰させるため永久禁止とする（`[D-80]`）。本プロトタイプおよび本番SaaSでは、進行役による対話ログからの論点ミラーリング要約提示とGitHub PRレビュー形式のワンクリック確定に統合している |

## 5. データモデル仕様（14テーブル）

`prisma/schema.prisma` に定義された14テーブルの役割と仕様：

| テーブル | 役割 | 主要カラム・設計意図 |
| :--- | :--- | :--- |
| `Learner` | 受講者マスタ | `learner_id`（UUIDv5） |
| `Session` | 演習セッション | `session_seq`（連番。中断・再開・削除が混じるため日時から復元不可）、`window_blur_duration_sec`（画面外滞在時間・記録専用で判定には使わない） |
| `Rating` | 評点の正本 | `scorer_model_version` / `stimulus_type` / `anchor_status` / `stimulus_features`(JSONB) / `probe_consistency_score`。`rating_category` は nullable で、null は「未採点」（人間の確認待ち）を表す |
| `AnchorItem` | アンカー項目マスタ | `anchor_id`、`content` (JSONB) |
| `AnchorResponse` | アンカー応答ログ | 較正用アンカー項目とその応答。`pretest` / `operational` の2状態。**アンカーは無得点なので `Rating` に行を作らない**（0点を入れるとルーブリック上の「Level 0」と区別できなくなり較正を汚すため）。応答時点の `anchor_status` を凍結して保持 |
| `PromptTurn` | 対話ターンログ | 対話の全ターン全文。`role` は `user` / `assistant` / `mediator` を厳密に区別 |
| `ArtifactEditDistanceSeries` | 成果物編集履歴 | 成果物の編集距離の時系列および最終成果物の全量保存（Bradley-Terry比較判断経路） |
| `InjectedFlawMap` | 誤り・正常箇所マップ | 仕込んだ誤りの位置と類型、**および正常箇所のラベル**（過剰指摘判定に不可欠） |
| `LearnerPreliminaryJudgement` | CFF暫定コミット | Force Decision First / Mandatory Justification。進行役による対話内論点ミラーリング要約に対するコミットメント（`action`: approve/remand、`justification`: 確認・微調整理由）を記録（`[D-80]` 実装済み） |
| `VerificationFocusSequence` | コード検証順序 | 3ペイン検証パネルで受講者が選択したコードスパンと明示順序（`focus_seq`） |
| `ScoreFeedback` | 異議申立ログ | 判定への異議申立。不服方向（too_high / too_low等）および自由記述の理由を記録 |
| `EvidenceComponent` | 抽出根拠コンポーネント | 採点エンジン第1エージェントが抽出した根拠要素。評点だけでなく根拠そのものを永続化し、XAIレポートのハイライトの原材料になる |
| `RelianceMetrics` | 適正依存指標 | 適正依存の3指標（リスク防御力 CSR / 協働活用効率 CAR / 自動化バイアス ABI）。過剰指摘トラップ（正常箇所）と仕込み不備の両方に対する判断から算出（`[D-81]`） |
| `MediationProbe` | 介入プローブログ | ソクラテス型深掘り・What-if注入の1手ごとの状態推定・選んだ手・選定理由。**正答鍵は含まない**（誘出であって誘導ではないため） |

## 6. 環境構築と実行手順

### 6.1. ローカル起動（最速5コマンド）

```bash
npm install
cp .env.example .env      # DATABASE_URL はローカル docker-compose 設定と一致
```

## 7. 公開デプロイ手順（Vercel + サーバーレス PostgreSQL）

本番相当のクラウド環境へデプロイする手順：

### 1. サーバーレス PostgreSQL の準備
1. [Supabase](https://supabase.com) または [Neon](https://neon.tech) でプロジェクトを作成。
2. プーリング接続文字列（Transaction pooler / ポート 6543 / `?pgbouncer=true`）を取得。
   - 例: `postgresql://postgres:[PASSWORD]@[HOST]:6543/postgres?pgbouncer=true&connection_limit=1`

### 2. スキーマ適用とアンカーデータの初期シード
```bash
export DATABASE_URL="postgresql://postgres:[PASSWORD]@[HOST]:6543/postgres?pgbouncer=true"
npx prisma db push
npm run parse:anchors
npm run seed:anchors
```

### 3. Vercel へのインポートと環境変数設定
1. [Vercel](https://vercel.com) でリポジトリをインポート。
2. Environment Variables に設定:
   - `DATABASE_URL`: プーリング接続文字列
   - `OPENAI_API_KEY`: LLM API キー
   - `GEMINI_API_KEY`: （任意）Google Gemini API キー
3. Deploy を実行。

## 8. 意図的に作っていないもの（今後の開発スコープ）

本プロトタイプは「全体像（Viability）」と「コア評価技術の稼働（Feasibility）」の証明に集中しており、以下の要素は今後の本格開発・社会実装スコープとして意図的に切り離している（`[D-79]`）：

* **疑似対話形式（SCT型）アンカーバンクの本格構築とチート耐性実測**: 現行プロトタイプは静的選択式による出題〜無得点記録パイプラインのFeasibility実証にとどめている。状況変化に対する判断更新を客観判定する疑似対話（SCT型）アンカー項目の本格作成、およびマルチLLMによるチート耐性の定量実測は後続フェーズに実施する。
* **管理画面・カルテの本番バックエンド**: 組織ダッシュボードおよび受講者カルテはモックUI（静的データ）として全体像を提示している。マルチテナントDB、ロール別権限・認証・SSO、本番リアルタイム集計パイプライン、課金管理は商用化に向けて開発する。
* **実務題材・誤り注入パイプラインの自動生成**: 現状は人手作成3シナリオから選択。要件定義〜設計工程の実務題材を体系的かつ動的に生成・誤り注入するパイプラインを構築する。
* **比較判断（Bradley-Terry）判定器・セマンティックDiff**: 現行の絶対採点方式から、課題横断での人間専門家一致（QWK $\ge 0.70$）を担保する判定パイプラインを実装する。
* **評価者HITL画面 / IRT較正・等化パイプライン**: 提携企業でのPoCおよびSMEパネルを通じた実データ収集を経て構築・較正する。
