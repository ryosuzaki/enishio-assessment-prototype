# Enishio Assessment Prototype 動作確認手順書

**対象リポジトリ**: `products/enishio-assessment-prototype`（縦切りプロトタイプ）  
**関連仕様書**: [AIアセスメントMVP定義書](../../enishio-education/docs/AIアセスメントMVP定義書.md) §4

---

## 1. はじめに（本書の目的と実証の全体像）

本書は、**「AIの出力を鵜呑みにせず検証・修正できる能力（評価的判断力・AI協働力）」**を対話ログから証拠付きで抽出・採点するアセスメントエンジンの縦切りプロトタイプについて、環境構築から画面操作、バックエンドデータ層の確認までの動作確認手順をまとめた資料です。

### 実証する縦切りフロー（端から端までの1セッション）

```
[STEP 1: セッション開始・課題選択]
   │  アンカー項目（全20項目）および動的課題（全3シナリオ）を選択
   │  受検者ID（UUIDv5）確定生成 ＆ session_seq（連番）発行
   ▼
[STEP 2: 共通アンカー項目解答]
   │  静的4択＋確信度（無得点記録・anchor_responses へ保存）
   ▼
[STEP 3: 動的課題対話セッション（3ペイン）]
   │  ① 左ペイン: 課題仕様（3シナリオから選択可能）
   │  ② 中央ペイン: 成果物エディタ（リアルタイム編集距離記録）
   │  ③ 右ペイン上: AI同僚チャット（マルチターン対話）
   │  ④ 右ペイン下: 検証フォーカスパネル（着眼箇所と順序の記録）
   ▼
[STEP 4: CFF（認知強制機能）暫定判断]
   │  ① Force Decision First: AIレポート閲覧前の承認/差し戻し判定
   │  ② Mandatory Justification: 理由記述の強制（空欄不可）
   ▼
[STEP 5: AutoSCORE 2段階自動採点 ＆ XAIレポート]
   │  ① 第1エージェント: 対話から検証根拠（スパン）を抽出（チャット上でハイライト）
   │  ② 第2エージェント: 抽出結果のみから軸4採点（0〜5点・確信度出力）
   │  ③ XAIレポート: レベル・確信度・根拠スパン・診断フィードバック
   ▼
[STEP 6: 異議申立（Score Feedback）]
      不服申立と理由記述（score_feedback へ保存）
```

## 2. 事前準備と環境構築

### 2.1. 動作前提条件
- **Node.js**: v18.17.0 以上（Next.js 16 / React 19 対応）
- **PostgreSQL データベース**: 同梱の `docker-compose.yml`（`docker compose up -d`）、任意のローカル PostgreSQL、または Supabase / Neon 等のクラウド環境
- **LLM API Key**: `OPENAI_API_KEY`（採点・対話モデルは `LLM_MODEL` および `EVALUATOR_MODEL` / `DIALOGUE_MODEL` / `MEDIATOR_MODEL` で切替可能、既定 `gpt-5.6-luna` `[D-59]`）
  > [!IMPORTANT]
  > **なぜ API キーが必須か（ローカル代替しない設計原則）**:  
  > APIキー未設定時にキーワード一致等のローカル判定で代替スコアを埋めると、単語の出現を検証行動と誤認し、かつ `rater_type = "llm"` の偽ログが残って `scorer_model_version` による追跡可能性・学術的監査性が崩れるため、**「採点できないときは採点しない（エラーを返す）」**設計となっています。

### 2.2. セットアップ手順

リポジトリルート（`products/enishio-assessment-prototype`）で以下のコマンドを順に実行します。

```bash
# 1. 依存パッケージのインストール
npm install

# 2. 環境変数ファイルの作成
cp .env.example .env
```

`.env` を開き、接続先データベースと API キーを設定します。同梱の `docker-compose.yml` を
使う場合、`DATABASE_URL` は `.env.example` の既定値のままで一致します。

```env
# PostgreSQL 接続文字列（docker-compose.yml の既定値と一致）
DATABASE_URL="postgresql://user:password@localhost:5432/enishio_education?schema=public"

# Anthropic API Key
OPENAI_API_KEY="sk-..."
```

```bash
# 3. ローカル PostgreSQL の起動（別途用意した DB を使う場合は不要）
docker compose up -d
```

続いて、データベーススキーマの反映と初期データのロードを行います。

```bash
# 4. Prisma クライアントの生成
npm run prisma:generate

# 5. DBスキーマ（14テーブル）のプッシュ
npm run prisma:push

# 6. アンカー項目のDB初期投入（出題に必須）
npm run seed:anchors
```

#### アンカー項目バンクの供給源

`npm run seed:anchors` は2つの供給源を持ちます。

| 供給源 | 中身 | 条件 |
| :--- | :--- | :--- |
| `src/data/anchors.json` | 運用中の共通アンカー項目バンク20項目 | 存在すれば優先される |
| `src/data/anchors.sample.json` | 公開デモ用サンプル2項目（リポジトリ同梱） | 上が無いときのフォールバック |

**運用バンク20項目はこのリポジトリに含まれていません**（項目露出の防止）。運用バンクを
使う場合は、隣の `enishio-education` リポジトリをチェックアウトしたうえで、`seed:anchors`
の前に解析を実行します。

```bash
git -C ../.. submodule update --init products/enishio-education
npm run parse:anchors     # Markdown → src/data/anchors.json
npm run seed:anchors
```

同梱サンプルで動作している間は、初期画面のアンカー項目欄に「公開デモ用サンプル」
バッジと注記が表示されます。**この表示が出ている状態を「運用バンク20項目で確認した」
と記録しないでください。**

## 3. 画面操作によるエンドツーエンド（E2E）動作確認手順

### 3.1. アプリケーションの起動
```bash
npm run dev
```
ブラウザで `http://localhost:3000` にアクセスします。

---

### 3.2. STEP 1: セッション開始・課題選択
1. **画面表示**: 初期画面（ヘッダー・概要・選択フォーム）が表示されます。
2. **出題する共通アンカー項目の選択**:
   - `T-05 バンク（全20項目）` から出題する項目をドロップダウンで選択（デフォルト: `ANCHOR-A-01`）。
3. **取り組む動的課題の選択**:
   - `T-06a タスクレジストリ（全3シナリオ）` から取り組む課題をドロップダウンで選択:
     - `[TASK-FINTECH-AUTH-01]` 金融決済APIのレートリミットおよびトークン検証ロジックのレビュー
     - `[TASK-ECOMMERCE-CANCEL-01]` ECサイト在庫管理・注文キャンセル/返金APIのレビュー
     - `[TASK-HELPDESK-PRIVACY-01]` 社内ヘルプデスクAIチャットボットのログ記録ミドルウェアのレビュー
4. **「セッションを開始する（アンカー出題へ）」をクリック**:
   - バックエンドで `generateLearnerId("tenant-jaist-demo", "examiner-preview-user")` により UUIDv5 が確定生成されます。
   - `sessions` テーブルに新規セッションが作成され、連番の `session_seq`（初回は 1）が発行されます。

---

### 3.3. STEP 2: 共通アンカー項目の解答（疑似対話・一場面切り取り）
IRT較正・等化のための共通アンカー項目（実務判断の一場面を切り取ったマイクロシチュエーション）が出題されます。

1. **状況・提案確認**: 実務レビューの一場面（状況ヴィネット）とAI同僚の提案文を確認。
2. **段階1（全体判断）**: 選択肢に答えを含めない「採用可否（そのまま採用 / 条件付きで採用 / 採用すべきでない）」の3択から選択し「この判断で確定する」をクリック（ロックされる）。
3. **段階2（懸念領域）**: 懸念の所在の粗い分類（4択）を選択し「次へ」をクリック（※類型C・不備無しの項目ではスキップ）。
4. **段階3（前提変化への判断更新）**: 差し込まれた新情報を確認し、方針の妥当性の移動（-2〜+2）を選択。
5. **段階3b（反論耐性、該当項目のみ）**: AI同僚からの新情報を含まない反論に対し、判断を再選択。
6. **段階4（確信度評定・5段階）**: 1（全く自信なし）〜 5（非常に確信）を選択し「アンカー回答を送信・記録する」をクリック。
7. **アンカー解答完了画面**: 記録完了（`anchor_status = pretest`、無得点運用）を確認し、「動的対話セッションへ進む」をクリック。
8. **テレメトリ確認ポイント**:
   - 段階ごとの解答時間（ms単位）、シャッフル提示順、確信度が `anchor_responses` テーブルに記録されます。
   - **`ratings` テーブルには行を作成しません**（アンカーは無得点運用のため、0点を入れてルーブリックのLevel 0と混同させるのを防止）。

---

### 3.4. STEP 3: 動的課題対話セッション（3ペイン検証環境）
選択した動的課題の3ペイン構成検証ワークスペースが開きます。

```
┌─────────────────┬──────────────────────────┬─────────────────────────┐
│  左ペイン       │  中央ペイン              │  右ペイン（上部）       │
│  【課題要件】   │  【成果物エディタ】      │  【AI同僚チャット】     │
│                 │                          │                         │
│  選択した課題の │  AI同僚の初版ドラフト    │  AIへの質問・指示       │
│  業務要件・制約 │  （編集すると差分距離を  │  不備の指摘・議論       │
│  仕様書         │    リアルタイム記録）    ├─────────────────────────┤
│                 │                          │  右ペイン（下部）       │
│                 │                          │  【検証フォーカス】     │
│                 │                          │  着眼コードスパン選択   │
└─────────────────┴──────────────────────────┴─────────────────────────┘
```

1. **左ペイン（仕様確認）**:
   - 選択した課題の業務要件・制約条件・セキュリティ基準を確認。
2. **右ペイン上部（AI同僚チャット）**:
   - AI同僚に対して不備の指摘や修正指示を入力して「送信」。
   - AI同僚からの返答を受け取り、対話を通じた検証を行います。
   - 対話内容は `prompt_turns` テーブルに逐次記録されます。
3. **中央ペイン（成果物編集）**:
   - コード内の問題箇所を直接修正します。
   - 編集を行うと、元のコードからのレーベンシュタイン距離が計算され、`artifact_edit_distance_series` テーブルに時系列で記録されます。
4. **右ペイン下部（検証フォーカスパネル）**:
   - 中央ペインのコードから疑わしい行を選択し、「フォーカスに追加」をクリック（またはメモを入力）。
   - 明示的な着眼順序（`focus_seq` 1, 2, 3...）が `verification_focus_sequences` テーブルに記録されます。
5. **画面上部右「レビュー完了 ➔ 暫定判断へ進む」をクリック**。

#### 3.4b. 媒介の状態推定パネル（ソクラテス型深掘り・What-if注入）

AI同僚への指摘を送信するたびに、対話ログの現状から「媒介の状態推定（走行中）」パネルが自動更新されます。

1. **状態推定カード**: ルーブリック（軸4）が求める5つの根拠カテゴリ（前提の言語化・トレードオフ・要件への紐づけ・正常箇所の弁別・前提変化への頑健性）それぞれについて、「取得済み／部分的／未取得」を表示します。
2. **選んだ手**: 推定を踏まえてメディエーターが選んだ手（深掘り・What-if注入・自己申告・見送り）と選定理由。
3. 手が選ばれた場合、進行役（媒介プローブ）としての問いが対話ログに追加され、通常のAI同僚とは別の見た目（シアン系・イタリック）で表示されます。**この問いに答えると、次の送信時にまた状態推定が更新されます。**
4. 1セッションあたり最大4手（MVP 2.1 の「3〜4ターン」に対応）。上限に達すると以降は手を打ちません。
5. **確認ポイント**: メディエーターへは仕込み不備の位置を渡していません。パネル下部の注記（「メディエーターには仕込み不備の位置を渡していません」）がその設計を明示しています。

---

### 3.5. STEP 4: CFF（認知強制機能）暫定判断
AI評価レポートを見る前に、受講者自身の判断を下します。

1. **① 成果物ドラフトに対する最終判断（Force Decision First）**:
   - `承認（Approve）`: AIの提案を採用・デプロイ可とする
   - `差し戻し（Remand）`: 修正・再検証が必要として差し戻す
2. **② 判断理由・根拠（Mandatory Justification）**:
   - なぜ承認/差し戻しと判断したかの技術的根拠・補足指示を入力。
   - **空欄やスペースのみの場合は次へ進めません**（クライアント側およびAPI側の二重バリデーション）。
3. **「暫定判断を確定し、AI評価を実行する」をクリック**:
   - `learner_preliminary_judgements` テーブルに記録され、AutoSCORE 採点パイプラインが起動します。

---

### 3.6. STEP 5: AutoSCORE 2段階自動採点 ＆ XAIレポート
1. **AutoSCORE 2段階パイプラインのバックグラウンド実行**:
   - **第1段階（根拠抽出エージェント）**: 対話ログから受講者の「検証行動」に該当する発話スパン・仕込み不備（`FLAW-01` 等）への指摘箇所を抽出。
   - **第2段階（採点エージェント）**: 抽出されたスパン情報のみを入力とし、軸4ルーブリックに基づいて 0〜5 点のバンドを判定し自己申告確信度を出力。
2. **XAIレポートの表示内容確認**:
   - **総合評点**: Level 0 〜 Level 5（または確信度 0.70 未満時の「確認待ち（pending_human）」表示）。
   - **採点確信度**: 例: `88%`
   - **検証行動の根拠一覧**: どのターンのどの発言（`quoted_span`）が評価されたかがチャットログ上でハイライト表示。
   - **診断的フィードバック**: 強み、見落とされたリスク、今後の改善アドバイス。
   - **深掘りへの応答の一貫性（Probe Consistency）**: 3.4b で深掘りが発生していれば、その応答の一貫性スコアと判断理由。発生していなければ「判定対象がありません」と表示される。

#### pending_human（評点保留）経路のデモ実演

「採点できないときは採点しない」（README）の帰結として、確信度が閾値未満のときは評点を確定させず `rater_type = pending_human` として記録する。**確信度はモデルの自己申告のため、通常の対話では意図的に発火させにくい。** デモでこの経路を確実に見せたい場合のみ、`.env` に以下を設定してから `npm run dev` を再起動する。

```env
# 既定は0.70。0.99等に上げると、通常なら確定するはずの確信度でも保留経路に入る。
HITL_DEMO_CONFIDENCE_THRESHOLD="0.99"
```

**`scoring_confidence`（採点器が実際に返した値）自体は変更されない。**変わるのは確定させるかどうかを決める運用パラメータだけであり、画面にもその旨が注記される（「この閾値は `HITL_DEMO_CONFIDENCE_THRESHOLD` によりデモ用に引き上げられています」）。デモ終了後は `.env` から当該行を削除して再起動し、既定の0.70へ戻すこと。

---

### 3.7. STEP 6: 異議申立（Score Feedback）の送信テスト
1. レポート下部の「評点に対する異議申立・フィードバック」を展開。
2. **不服の方向性**を選択:
   - `評点が高すぎる` / `評点が低すぎる` / `軸の割り当てが違う` / `根拠として示された箇所が違う`
3. **申立理由（自由記述・必須）**を入力:
   - 例: `ターン3で指摘したキャッシュ不整合のトレードオフが根拠から漏れています。`
4. **「異議を申し立てる（記録）」をクリック**:
   - `score_feedback` テーブルに記録され、送信完了メッセージが表示されます。
5. **「← トップへ戻り最初からやり直す」**をクリックすると、セッション状態がリセットされ初期画面へ戻ります。

## 4. バックエンド・CLI・テスト検証手順

画面を操作せずに、データ層、パーサー、テスト、セキュリティチェックの健全性をコマンドラインから確認できます。


### 14テーブルの確認ポイント

| テーブル名 | 確認する主なカラム・データ |

## 6. トラブルシューティング

| 症状 | 原因 | 対処法 |
| :--- | :--- | :--- |
| `Environment variable not found: DATABASE_URL` | `.env` が存在しないか設定が不正 | `.env.example` をコピーして有効な PostgreSQL 接続文字列を設定 |
| `アンカー項目が見つかりません` / 出題時にエラー | DBにアンカー項目が入っていない | `npm run seed:anchors` を実行（運用バンクを使う場合は先に `npm run parse:anchors`） |
| 出題画面に「公開デモ用サンプル」バッジが出る | `src/data/anchors.json` が無く同梱サンプルへフォールバックしている | 運用バンクで確認したい場合は `enishio-education` をチェックアウトし `npm run parse:anchors` → `npm run seed:anchors` |
| `AI Evaluation Error` / 採点が進まない | `OPENAI_API_KEY` が未設定または残高・権限エラー | 有効な LLM API キーを `.env` に設定してサーバーを再起動 |
| ビルド時に型エラーが出る | Prisma クライアントがスキーマと不整合 | `npm run prisma:generate` を実行後に再度ビルド |
| `session_seq` の重複例外 | 複数同時アクセス時の連番競合 | `startSession` 内部で最大5回自動リトライされるため通常は自動復元 |
